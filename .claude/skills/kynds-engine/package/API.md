## `core/BuildJobs.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M2): time-sliced building. A big piece of generation (a lot's scenery and furniture, a cottage, a stretch of kingdom) is written as a generator that `yield`s between steps; the scheduler runs steps from the queue each frame until its time budget is spent, so nothing builds in one long stall (the "pop-in" hitch). Anything that needs a result at once can `finish` its job there and then: the same steps, run back to back. Headless: no three.js, no DOM. The clock is injectable for tests.

## `render/MaterialFeatures.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M5): material features. A feature is one look a material can carry (tri-planar surface detail, snow on top, a coat's sheen), written twice: as a GLSL patch for today's WebGLRenderer, and as a TSL node graph for WebGPURenderer. A material records the features it carries and their settings (`featuresOf`), so it can be rebuilt as a node material (`toNodeMaterial`) once every feature it carries has a TSL version. The WebGPU build of three.js is a separate copy of the library, so nothing here imports it: the caller that renders with nodes passes the `three/webgpu` and `three/tsl` modules in.

## `render/backend.ts`

The render backend (Kynds Engine M5b). The classic build draws with WebGLRenderer. The WebGPU edition is the same code built with `three` mapped to `three/webgpu` (`npm run build:gpu`, or `vite --mode gpu`; see vite.config.ts): one copy of the library, which has WebGPURenderer (with its own WebGL2 fallback) and no WebGLRenderer. Everything that makes a renderer goes through `createRenderer`, so game code never names either class. WebGPURenderer draws node materials. Plain materials it converts itself; a material carrying features (MaterialFeatures) or a hand-written shader with a port gets its node version from `prepareForGPU`, run over a scene before it's drawn. A GLSL shader with no port can't be drawn at all, so its mesh is hidden (and named once in the console) rather than breaking the frame.

| --- | --- | --- |
| `GPU_EDITION` | const | True in the WebGPU edition. |
| `VIEWPORT_FROM_TOP` | const | Whether a renderer's viewport and scissor are measured from the canvas's top edge (WebGPURenderer, either backend) rather than its bottom (WebGLRenderer). |
| `RendererOptions` | interface |  |
| `createRenderer` | function | Make a renderer: WebGLRenderer in the classic build, WebGPURenderer in the WebGPU edition. |
| `backendName` | function | Which backend is actually drawing: 'webgl' (classic), 'webgpu', or 'webgl2' (WebGPURenderer's fallback). |
| `gpuSourceOf` | function | The features (and shader port) a material drawn in the WebGPU edition came from. |

## `render/coplanar.ts`

Kynds Engine: no flicker inside a model. Procedural models are made of boxes, cylinders and planes that butt and overlap, and wherever two of them share a face's plane (a board's end flush with the side of the board it meets, two crates side by side) the depth buffer can't tell them apart and the faces flicker (z-fighting) as the camera moves. `separateCoplanar` finds the pieces whose faces share a plane (a box's faces exactly, the flat ends of a cylinder, the outer planes of anything else, and the real faces of merged geometry) and moves one of each such pair a few millimetres, along the one axis where they meet: a solid piece grows along it about its own centre (only deepening overlaps that are already there, so no gap opens), a thin one (a slat, a band, a decal) slides along it instead, so it never gets visibly thicker. The largest pieces stay exactly as built, and so do merged geometries (their inner faces would move unpredictably), skinned, instanced and see-through pieces, and any mesh marked `userData.exact`.

## `render/merge.ts`

Draw-call reduction for procedurally built models. Each little box or lathe is its own draw call (and another one in the shadow pass); merging meshes that share a material cuts a cottage full of props from hundreds of calls to dozens without touching how anything looks. Meshes flagged `userData.keep = true` (toggled or animated on their own) are never merged.

## `render/release.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M3): freeing what a part of the world held on the GPU once it is unloaded, without breaking anything still on show. Builders share a great deal (cached materials and textures, one geometry instanced across lots, clones for the map), so counting references by hand would be fragile. Instead this works like a collector: whatever `gone` reaches that none of the `kept` roots reach is released. Releasing in three.js is never fatal: anything used again is simply uploaded again, so a missed share costs a re-upload, not a broken frame.

## `sim/Archive.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M4): the persistent memory store. When someone leaves the simulated world (dies, moves away, is demoted past the last tier), what made them who they were is written here, keyed by id, and kept through saves: the live world can let them go without the story forgetting them. Bounded, so a long game's archive can't swallow the save: past `limit`, the longest-held records go first (records marked `keep` never do). Game-agnostic and headless: what a record holds is the game's business.

## `sim/SimTiers.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M4): simulation tiers. Not everyone in a world is simulated the same way: those where play happens are simulated step by step, those elsewhere in broad strokes, those on the road only until they arrive. The game names its tiers and says which each agent is in, every tick; this keeps the books, so a promotion (arriving where play happens) or a demotion (leaving it) is one event a game can hook, and the numbers in each tier can be watched. ## `sim/save/pack.ts`

Kynds Engine (docs/ENGINE_PLAN.md, M4): text packing for saves. Saves are JSON full of repeated keys and ids; a dictionary coder (LZW with literals, as the lz-string format does it) shrinks them several times over, and the result is written 15 bits to a UTF-16 unit (offset clear of control characters and well below the surrogate range), so it stores safely in any Web Storage. Synchronous on purpose: saving and loading stay simple calls. Headless (no DOM).

| --- | --- | --- |
| `pack` | function | Pack a string (any UTF-16 text) into a shorter one. |
| `unpack` | function | The text `pack` was given; null if this isn't packed text (or it's damaged). |
